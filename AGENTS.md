# Agent Workflow

## Source of truth for numbers

Tracked result pages live under `result/<profile>/<suite>/<fork12>-<upstream12>[-vendor].md`, one
page per measured `(suite, hardware profile, fork revision, upstream revision, vendor arm)`, and
are generated from the raw run under `data/results/<profile>/<suite>/<timestamp>/`. Do not
duplicate result tables into `README.md` or into docs. Historical reports are not maintained; use
git history.

`result/INDEX.md` is generated by `scripts/gen_index.py`. Never edit it by hand.

## Every published number carries its fork revision, its upstream baseline and its vendor

A measurement without the commit it was taken at is not evidence. `run.yaml` records the measured
fork checkout's path, commit, dirty state, version and features; the upstream `faer` revision and
the ref it was pinned by; the harness commit and dirty state; the host; the thread environment; the
CPU set used at each thread count; the vendor library the LAPACK arm was linked against (its
version, build configuration and the kernel its runtime dispatched to); the guard logs; and the
timing policy. `scripts/validate_run.py` refuses to accept a manifest whose fork or upstream commit
does not resolve, or whose declared engines include a vendor arm with no vendor identity. If you
quote a number anywhere, quote its fork revision, its upstream revision and its harness with it. A
result depends on three independently moving revisions, and changing any one of them can move a
number.

## One vendor arm per run

The vendor row's name is not chosen by whoever writes the row: the harness derives it from the
library the binary linked, so it emits `lapack-openblas` or `lapack-mkl` because that is what it
loaded. The two are mutually exclusive in one process — they define the same symbols — so
`--vendor` selects an arm at build time and an arm is a whole run, with its own manifest, its own
page and its own two faer rows. Do not merge two arms into one manifest or one page: `vendor`
describes the one library that produced those numbers, and a manifest naming two would describe
neither. The recorder refuses a run whose harness reports a vendor other than the arm requested,
and the validator refuses a manifest whose vendor is not the one its engines name. MKL reports no
dispatched-kernel name and no processor count; its manifest leaves both empty rather than infer
them, and the page says so.

## Timing discipline

One measurement at a time, and **no build while a measurement is running**. `scripts/record_run.py`
holds one campaign-level lock across build, verify and timing for exactly this reason; a lock inside
a per-revision target directory would let a second recorder build another revision during a
measurement. Every timing goes through this repository's protocol script
(`benchmarks/scripts/pinned.sh`, which the harness owns because faer has no `benchmarks/` directory
of its own); it pins the cores and checks that those cores **and their SMT siblings** were idle
before and after, and a run spoiled by other load is discarded, not published.

The observing side is pinned too, because unrelated work on the measured cores is what the idle
guard then has to reject. The rule is not machine-specific: a cell's measured threads sit in one
L3 domain, and everything else - the agent, the recorder, the guard checker - runs on the CPUs
outside that domain. The recorder derives both sets from the machine's own topology, refuses to
start when its affinity overlaps the measured set (SMT siblings included) or when a declared CPU
set spans more than one L3 domain, and names the derived free CPUs in the refusal. The affinity
lives in the process, so the agent's own pin must be re-established after a restart; the profile
for the current host records the concrete CPU sets and their cache sizes.

Priming is **time-based** and identical on every arm. A fixed
call count is not a substitute: after an idle gate this host reads low for the first second or two
of sustained AVX-512 work, which is large enough to be mistaken for a kernel defect.

A thread budget is declared, not inherited. The harness sets the vendor library's own thread count
from the row's budget and reads it back before measuring, and the recorder removes the ambient
thread variables from the measured process's environment.

Correctness precedes timing. `fbench verify` must report a clean grid for every population and
thread count before any timing pass; the recorder enforces this and publishes nothing otherwise.

## Coverage is data, not an apology

The campaign is not run in full on every profile for every commit. A partial run is legitimate: it
is recorded, it is marked `partial` in the index, and it never displaces a full-coverage report. Do
not describe a partial run as if it covered the suite, and do not infer "no regression" for a
population the run did not contain. Cases a provider cannot take are recorded as `skipped` in the
run's own CSV and in `run_spec.populations[].skipped`, not silently dropped.

## The harness is a third identity

`fbench` lives in this repository and is linked to the measured libraries by path. It is not
written yet (`fbench/Cargo.toml` is a placeholder with no `src/`). When it lands, a change to it
that can move a number invalidates the evidence exactly as a library change does — the harness
commit is recorded per run and repeated in every page header. The currency computation in
`result/INDEX.md` covers the two pinned libraries; a harness change does not move a pin, so the
manifest and the page header are where it is visible.
