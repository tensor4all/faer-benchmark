## What the change reaches

Everything dense: `Par` is no longer `Copy`, workspace queries take `ParShape`, the process-wide parallelism
is gone, the arch-keyed serial rates and outside costs move the `Par::Rayon` gates of every family on this
host (`HostClass::x86_64-avx512`), and `t4a-private-gemm-x86` 0.1.25's race fix changes every parallel x86
GEMM. So there is no family the change cannot reach; the collateral cells are the families the daily subset
does not otherwise cover (`full_piv_lu`, the `qr` composite, `triangular_solve`).

## The harness

One commit on `harness/faer-0.25`. The fork rows build a `Par` per call (`ParCfg`) and use explicit-parallelism
entry points only; the upstream row keeps the high level calls and its own global setting inside the held
spindle group (`measure_row`). The one API difference the library is not edited for, `*_scratch(.., Par)`
(0.24.x) against `(.., ParShape)` (0.25), is selected by the harness feature `fork-par-shape`, which
`scripts/build_for_faer_rev.sh` turns on when the fork checkout declares `pub enum ParShape`. The build
script keeps the lock the build resolved beside the binary (`Cargo.lock.resolved`, hashed in
`BUILD_LOCK_SHA256`) and restores the committed `Cargo.lock` byte for byte, because a fork at another version
rewrites it. The harness commit and its build inputs are the same for both revisions.

Both revisions were built through the script only, MKL arm, and `fbench verify` passed on the grid below at
1/4/8 T for both before any timing (see the verify files in each run directory; the recorder repeats it).

## Grid (declared before the runs)

Settings are the frozen ones: prime 250 ms, 5 calls, `--statistic median`, boost off (`cpufreq/boost` = 0),
this session pinned to the observer CPUs 0-3,12-15, measured sets 1T `4`, 4T `4-7`, 8T `4-11`, whole-domain
idle guard, `PINNED_RETRIES=8`.

Recorder arguments, suite `faer-kernels`, arm `--vendor mkl`:

```
--engines faer-fork,faer-upstream,lapack-mkl --aa 3 --reps 5 --prime-ms 250 --threads 1,4,8 --dtypes f64,c64
--shapes 64,256,1024x64,64x1024,64x64x64,256x256x256,4096x64x64,16x4096x240,4096x16x240,64x64x4096
--families gemm,lu,qr_factor,cholesky,svd_values,svd_thin,eigh,householder_apply,solve
```

* shapes: one square per small and mid tier (64, 256), the tall (1024x64) and wide (64x1024) shapes, and for
  `gemm` the daily triples (64^3, 256^3, 4096x64x64, 16x4096x240, 4096x16x240, 64x64x4096).
* orders: both, `c` and `f`. The recorder has no order selector and the manifest declares both, so F is not
  recorded alone; C is the order that exercises the row-major paths the candidate touches.
* dtypes: `f64` and `c64`; `f32`/`c32` are not in the daily subset.
* rows: all three of the MKL arm. A first attempt with the two faer rows only (`--aa 2`) was recorded in full
  (`data/results/zen5-cpu/faer-kernels/20261026T142443Z-pair-base-1`) and then refused by the validator
  ("the manifest records vendor 'mkl', but no declared engine is backed by a vendor library"). It is discarded,
  not used, and stays as a rejected run; the vendor row is measured because the arm requires it.
* large tier, suite `faer-kernels-large`, 4T and 8T only (the suite declares no 1T): `--shapes 1024,1024x1024x1024`,
  `--dtypes f64`, families `gemm,lu,qr_factor,cholesky,svd_values,svd_thin,eigh,solve` (the suite declares no
  `householder_apply` there), same settings.
* collateral, suite `faer-kernels`: `--families full_piv_lu,qr,triangular_solve --shapes 64,256 --dtypes f64 --threads 4,8`.

Order of recording: baseline, candidate (main grid), then the large tier and the collateral run, baseline first
each time. A second main pair in the opposite order (candidate, baseline) follows only if the budget allows; if it
is recorded both attempts are kept and reported.

## Trimmed, and why

* the 4096x256 and 256x4096 shapes (the two largest cells: about 60% of a process set's time on the first
  attempt), `f32`/`c32`, the 1536 and 2048+ tiers, `full_piv_lu` and `qr` outside the collateral cells, the
  96/128/384/512/768 squares, `c64` at 1024, and every 1T cell of the large tier: outside the daily subset or
  over the budget for the pair (about three hours). The 4096x256 QR/Householder cell therefore has no direct
  evidence here; 1024x64 stands in for the tall class.
* the publication run (full suite, both arms) is not part of a merge and is not run here.

## Decision rules (also declared before)

1. `scripts/candidate_compare.py` refuses a pair whose unchanged `faer-upstream` median is not within 2%: no merge,
   no retry with another band.
2. Per family, over its target cells: median candidate/baseline ratio above 1.05, or any single cell above 1.20
   that is also outside both revisions' own between-start ranges (a tail cell the pages already flag with `!`
   does not count) stops the merge; that is the maintainer's adoption call.
3. Otherwise merge by fast-forward of `main` to `1477bdf`, confirm the tree hashes, record `PATCHSET.md` and the
   worklog with the run directories, move `pins/t4a-faer.rev`, publish, tag.
