# Throughput charts - timing-v2 baseline (faer-kernels)

Generated by `scripts/throughput_report.py` from the recorded runs below; no timing is run here.
**Nominal** GFLOP/s: one algorithmic operation count per family, so sizes are comparable within a family and absolute values are not comparable across families. The count is stated under every chart and in each data table.
Error bars are the between-start sample SD of the process medians, not a confidence interval. The `!` cells of the measured pages are included as they were recorded.
`faer-fork`, `faer-upstream` and `lapack-mkl` come from one recorded run and therefore from one process each; `lapack-openblas` comes from the other arm (its own binary), so its absolute level carries the between-arm uncertainty.
Recorded sizes: the daily suite gives 32-768 at 1T/4T/8T; the large-tier run adds 1024 at 4T and 8T for the plotted families (f64, C order). A line stops where a size was not measured - nothing is interpolated.
The 1024 points are a separate recording from the 32-768 points, so they carry their own run-to-run uncertainty on top of the between-start bars. Where the large-tier run is at the same fork revision as the daily run, the code is the same at 1024 (the row-major copy floor, `faer#23`, only changes shapes below 4096 elements).
Revisions: daily mkl: fork `0e15729`, upstream `0539947`, harness `1fd29fc`; daily openblas: fork `0e15729`, upstream `0539947`, harness `fc1269a`; large tier mkl: fork `0e15729`, upstream `0539947`, harness `75b8a1f`. No run was given for large-tier OpenBLAS (none recorded at this fork revision, and an older recording is not mixed in), so the series that would use it stops at the sizes of its other run.
